# docs

設計の経緯と決定を置く。コードを書く前に、上から順に1つずつ決める。

| 順 | ファイル | 決めること |
|---|---|---|
| 1 | `01-strategy.md` | なぜ作るのか、誰の何を満たすのか。プロダクトの一文定義 |
| 2 | `02-scope.md` | 何を作るのか。機能の一覧（`F-xx`）と、MVP に入れないもの |
| 3 | `03-structure.md` | 情報をどう組織し、操作がどう流れるか。画面の一覧（`S-xx`）と遷移 |
| 4 | `wireframes.html` | 全画面の配置と見た目。HTML と CSS で実際に作って確かめる |
| 5 | `04-tech.md` | 上の決定を実装の技術に落とし込む。バックエンド、ホスティング、データのモデル |

## 配置と見た目は wireframes.html で作る

配置（Skeleton）と見た目（Surface）は、文書にしない。Structure が決まったら、すぐ `wireframes.html` に全画面を並べて作り、ブラウザで見て直す。

- 1つの HTML ファイルに、`03-structure.md` の画面（`S-xx`）をすべて並べる。画面ごとに ID と名前を見出しに書く。
- 色・書体・余白は CSS の変数にまとめる。実装のときに `src/styles/global.css` へ移す。
- 配置や見た目で判断した点（選ばなかった案と理由）は、該当する画面の横に短い注記として残す。

## 文書の書き方

- 各文書の冒頭に、状態（検討中／確定）と日付を書く。
- 判断が要る点は、文書の末尾に「判断事項」として `Q番号` を振り、本文から `→Q番号` で参照する。選択肢、決定、理由を残す。
- コード中のコメントからは「Scope Q14」「04-tech 6章」のように参照する。
- 後から決定を変えたら、消さずに変更の日付と理由を追記する。
